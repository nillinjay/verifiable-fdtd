`verdict_exit` checks in this order:

1. **`63`**: `readout['criteria']` is absent, is not a dict, or is empty. An empty block declares
   nothing, and `all()` over an empty block would be vacuously true, so an empty block is refused.
2. **`62`**: `readout['negative_control']` is absent or not a dict (missing). Or `executed` is not
   exactly `True`, or `observed` is empty or `None` (vacuous). Or `status` is not
   `'failed-as-required'` (passed in the wrong direction).
3. **`61`**: an entry of `criteria` is not exactly `True`. The message names every violated
   entry, e.g. `verdict 61: pre-declared criteria violated: C1`.
4. **`0`**: none of the above.

The control is checked before the criteria. If a run's control cannot fail, the run has not shown
that its criteria can fail either. When both are broken, the result is `62`. The frozen tests do
not exercise that case, so the ordering is a choice this leg made.

Truth is tested with `is True`, not truthiness. A criterion of `1`, `'yes'` or `None` counts as
violated, and `executed=1` counts as vacuous. This is stricter than the contract and never more
lenient.

## Inferred intent, and how I checked it

- **Where "ran" is recorded.** The test docstring says that direction and evidence come from
  `status`, `executed` and `observed`. I read "ran" as needing both `executed is True` and a
  non-empty `observed`. The vacuous subtest sets both to false values at once, so it does not
  separate the two. The stricter reading refuses either one alone and never accepts something the
  test refuses.
- **The token that means "failed in the required direction".** The only passing value in the
  tests is `'failed-as-required'`, and the wrong-direction test uses `'passed'`. I accept only the
  exact string `'failed-as-required'`. Any other status is `62`.
- **The message channel for `61`.** The test redirects stdout and stderr together, so either
  channel works. stderr keeps the driver's stdout limited to the one JSON line per case.
- **Purity under the stub.** The tests replace `parity` with a module that exposes only `np`. So
  the driver now imports `sys` itself (`:25`), where it used to get `sys` through
  `from parity import *`. `verdict_exit` uses nothing else from the module.

I also checked behaviour outside the frozen file, in memory, with `parity` stubbed:
`negative_control_evidence` with the archived numbers (baseline `7.50792e-07`, control
`0.34032`) gives `failed-as-required`, and the verdict is `0`. A control of `1e-3` against that
baseline gives `passed` and `62`. A run with no control row gives `not-run`/`executed=False` and
`62`. `criteria={}` gives `63`. `{'C1': 1}` gives `61`.

## What a real leg-15 run would now return

`configs/leg15-closure.json` declares hypotheses `H1`-`H4`. These are statements to attribute, not
pass/fail criteria, and neither the config nor the driver evaluates any criterion. So `main()` does
not invent a `criteria` block. It does not turn the hypotheses into booleans, and it does not
copy booleans from the config, because that would let a config declare that it passed. **A real
leg-15 run through this driver therefore exits `63`**: the run executes, and the readout records
`exit_status: 63`. That is the contract's answer for a readout that states no criteria. To make
the driver able to exit `0`, a later leg would have to pre-declare leg-15 criteria and their
evaluation. That leg would touch `configs/`, which is outside this leg's write set. This leg does
not do it. The candidate assertions already exist as the ladder tests in
`checks/test_leg15_closure.py` (C3 baseline reproduction, the PML ladder, the linear-in-`r` law,
the unrelated knobs, and the null/control).

No archived leg-15 run exists in this workspace (`runs/*/readout.json` has no
`leg15-closure-v1`), so no recorded number was read or changed.
