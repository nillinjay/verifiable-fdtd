## What the opt-in changes

Set `TORCHFDTD_ADMISSION_MODEL=forward-v1` and enter `torch.no_grad()` before calling the solver. The forward-only path is selected only for real, nondispersive, uniform, fused CUDA execution, without stored magnetic-wall faces, with synchronous device checkpoints and the existing fused-allocation bound. Gradient-enabled calls, other checkpoint tiers, tensor-workspace cases and unsupported topologies keep the original bound. The execution callers in `differentiable.py:805` and `mode_injection.py:213` retain forward-only admission when gradients are disabled and retain the full adjoint bound when gradients are enabled. Both `estimate_adjoint_memory` and resident `plane_reservation` explicitly disable forward-only admission, including under `torch.no_grad()`. Thus both point-estimator and plane-mode resident batch admission use the full adjoint bound before replay enters `torch.enable_grad()`, preserving the shared `AdjointBatchOptions.gpu_budget_bytes` check for the active solver and its unified material-copy/gradient-transfer carriers. During batch replay the device-protection check at `differentiable.py:805` runs with gradients enabled and also uses the full bound. The batch budget excludes caller geometry/input storage, objective and optimizer graphs, CUDA context, unrelated allocations and OS file cache; CPU batch outputs, accumulation carriers and metadata have separate host/output checks. This closes the forward-versus-adjoint under-reservation in the two resident planning paths; it does not establish a universal no-out-of-memory guarantee for other workloads or concurrent external allocations. Execution selection occurs before `_FDTD.apply`, not inside its always-gradient-disabled `forward` method.

def accumulate(self, output, samples, start):

A corrected-path GPU refusal includes `required_bytes`, `limit_bytes`, `unused_slot_reservation_bytes`, `omitted_unused_slot_bytes`, `unused_slot_count` and `reason=grad_disabled`.
