# Leg 8 evidence — `S1` BFAST scoping assessment — 2026-10-18

Contract: `plan.md`, section `LEG 8 REGISTERED — S1 BFAST SCOPING ASSESSMENT`, committed as `52fb678`
**before** this work. **No implementation. No kernel change. No simulation.**

**Recommendation: decline the BFAST kernel implementation for now.** The reasoning is below, and the
alternative is named.

## C1 — what BFAST actually is, from citable sources

**BFAST is a split-field / field-transformation method.** It splits each component of the transformed
electric displacement (and the corresponding magnetic field) into two parts and adds an auxiliary
field, so that the oblique phase is carried **inside the update equations** rather than in the
boundary condition.

Sources used:

| source | what it establishes |
|---|---|
| vendor page, "Broadband Fixed Angle Source Technique (BFAST)" | the method exists and applies to a periodic structure illuminated by a **broadband** source at an angle |
| vendor page, "Understanding injection angles in broadband simulations" | the defect it fixes: with Bloch boundaries the **injection angle varies with frequency**; the vendor says the same issue affects mode sources too |
| vendor page, "Bloch BCs in broadband sweeps over angle of incidence" | the vendor's own worked example: in a broadband sweep each simulation returns data at a **different angle per frequency** |
| literature: split-field FDTD for oblique incidence on periodic structures (Opt. Lett. **34**, 2453 (2009)) | the split-field scheme and its extension to dispersive/metallic structures |
| literature: wideband material-independent FDTD for periodic structures at oblique incidence (IEEE Trans. Antennas Propag., 2013) | the wideband split-field formulation |
| open review: *FDTD Modeling of Periodic Structures: A Review*, arXiv **2007.05091** | the family's drawbacks, quoted under C3 |
| previous project (REA) | the vendor exposes `use bfast fdtd`, `bfast alpha`, `bfast dt multiplier`. **The third name is evidence that the time step itself is modified.** Class `D`/`R`, implementation gap open |

## C2 — why it fixes the drift, stated as a claim

**This project's own measurement** (leg 7, criterion `C2`): with a fixed Bloch phase the propagation
angle falls as the wavelength rises. Over `1.50`–`1.60` µm the drift is **`0.4002` degrees**.

**The mechanism, as documented:** the Bloch boundary applies **one phase** for the whole run, so
`k_parallel` is fixed and `theta(f) = asin(k_parallel / k0(f))` falls with frequency. BFAST instead
freezes the **angle**: the split-field formulation carries `k_parallel / k0` in the update equations,
so every frequency in the band sees the same angle by construction.

**Stated as a claim, not as a verified fact.** I have not checked this against a vendor run or against
a numerical experiment. It rests on the vendor's documentation and on the structure of a split-field
scheme. Evidence class `D`.

## C3 — the vendor's divergence warning, carried

The previous project recorded the vendor warning that silicon / low-loss materials **may diverge**
from the numerical-permittivity gain. The open review states the family-level reason:

> "Many of the periodic boundary condition techniques have serious drawbacks, including the need to
> **modify the standard FDTD algorithm**, the need to consume **substantial computational resources**
> and **the inability to maintain a high Courant stability limit at oblique angles**."

Three consequences, and the third is the one that matters:

1. the standard update is replaced, so this is not an additive opt-in;
2. the recovery name `bfast dt multiplier` means the **time step is changed**;
3. **the Courant limit degrades at oblique angles**, which is exactly the regime the feature exists
   for, and exactly the material class this project uses (silicon, low loss).

## C4 — the cost, against a baseline measured here

The `1.2x` figure is a **vendor claim** (class `D`). The cost is not the runtime — it is the
**verification cost**.

| item | value |
|---|---|
| our measured baseline | the leg-7 campaign ran 8 Bloch cells in `32` s, about `4` s each, at `6000` steps |
| a `1.2x` BFAST run | about `5` s — negligible |
| if the degraded Courant limit forces a smaller step | cost scales as `1/dt`, so `2x` to `4x` is plausible — still seconds |

**Runtime is not the binding constraint.** The binding constraint is that **no open-source FDTD
implements BFAST.** Meep has an open request for it (issue #1991) that was **closed without an
implementation**. Every number this project calls `verified` rests on an **external reference** (rule
`V-0`, track `V`). A kernel change with no open-source counterpart has no `V4` cross-code reference
and no independent implementation to check against. The verification cost is therefore not seconds;
it is the whole `V1`-`V2`-`V3` apparatus rebuilt for a new update equation.

## C5 — the falsification route, before any code

**The cheapest test is a requirements test, not a physics test.**

A broadband fixed-angle source solves a **broadband** problem. This project's runs are **single
frequency**: every driver here evaluates at one wavelength (`C0 / lambda`). At a single frequency
there is **no drift to remove** — the measured `0.4002` degrees is a property of a band, and a
single-frequency run has no band.

So the smallest test that can kill the requirement is:

1. state whether any registered capability needs a **broadband sweep in angle**;
2. if it does, run the **existing** Bloch source once per frequency with the phase set to hold the
   angle, `k_parallel(f) = (2 pi f / c) sin(theta)`. That is exact at every frequency by
   construction, costs one run per frequency, and needs **no kernel change**;
3. compare that sweep against the requirement. If it meets it, BFAST is unnecessary.

Step 2 is the alternative in C6, and it is testable today.

## C6 — recommendation, with the alternative

**Decline the BFAST implementation now.**

**Alternative: keep the Bloch source and declare its validity.** Oblique illumination is available
**one frequency per angle**. A broadband fixed-angle sweep is obtained by **one run per frequency**
with `k_parallel(f)` chosen to hold the angle. The measured `0.4002` degrees of drift is then a
**declared property of a single broadband run**, not a defect, because the platform does not use one.

Trade-off in one line: **this gives up the vendor's one-run broadband convenience and gives up
nothing else**, in exchange for not replacing the update equations and not carrying an unverifiable
kernel change.

Revisit BFAST when, and only when, a registered capability requires a **single-run** broadband
fixed-angle illumination and the per-frequency sweep has been shown not to meet it.
