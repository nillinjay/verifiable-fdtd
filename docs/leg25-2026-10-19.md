## Calculation and scope

The opt-in `forward-v1` model already included a live-allocation component in
its predicted process peak. CUDA capacity is derived from free memory, which
already excludes those live allocations. Comparing the inclusive process
prediction to free capacity therefore charged existing allocations again.

The process prediction and its headroom are preserved exactly. Let `S` be the
existing process subtotal and `L` its existing live component,
`max(diagonal_epsilon_bytes, live_allocated_bytes)`. The calculation now uses:

```text
memory_reservation_bytes = S + 8 MiB + ceil(S / 20)
own_subtotal = S - L
own_required_bytes = own_subtotal + 8 MiB + ceil(own_subtotal / 20)
```

One MiB is 1,048,576 bytes. The own subtotal receives its own headroom;
subtracting live bytes from the already-rounded process prediction would
incorrectly retain headroom on the live component. The CUDA capacity helper
and the explicit resident-byte admission use `own_required_bytes` on this
opt-in path. Both returned diagnostics and refusal text expose
`required_bytes` equal to `own_required_bytes`, with `live_allocated_bytes`
reported separately. The live count is sampled once per reservation.

`memory_reservation_bytes`, `gpu_reservation_bytes`, workspace components, and
`allocation_headroom_bytes` retain their existing inclusive process-prediction
meanings. No non-forward path gains new report fields or changes its
admission number. Gradient-enabled execution, adjoint planning under
`no_grad`, CPU execution, and unsupported forward topologies retain their
previous reservation logic.

The fork change is confined to `torchfdtd/adjoint_memory.py`, committed before
either GPU regression as `314666cf7230a89de616a400926525a4e416f07c`.
`checks/test_leg19_admission.py` was not edited. The new CPU regression's
