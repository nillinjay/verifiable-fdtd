## Decision procedure and boundaries

Rule V-0 is applied conservatively. No registered V1 (analytic case), V2
(invariant), or V4 (independent code comparison) checks exist here, so there is
no path to a `verified` label, including when a readout claims a passing check.

For each numeric leaf of a case's `measured` object, the procedure looks up the
historical target in the run's archived config. It requires a matching policy,
a declared historical source, a finite nonnegative tolerance, and a finite
numeric target/value. If a recorded target is present in the readout, it must
agree with that archived target. Relative error is recomputed as
`abs(measured - recorded) / abs(recorded)`; a zero target uses absolute error,
matching the two drivers. Passing the inclusive tolerance grants `consistent`,
meaning historical solver reproduction only. A missing or failed comparison
grants `unchecked` and explains why. Stored `relative_error` and
`within_tolerance` claims never determine a decision.

Every other numeric metadata leaf is also emitted, with `unchecked` and the
reason that no registered metadata check exists. Booleans are status, not
headline numbers. `recorded` and `relative_error` contain comparison evidence,
not additional measured headlines, and are not repeated as new results.
Measured SHA-256 digests are additionally labelled: exact equality of valid
digests grants `consistent` for material-array identity only, not physics.
Nested unknown numeric fields are discovered recursively. Missing archived
config is supported and yields `unchecked`; malformed stage declarations,
duplicate/missing case IDs, and non-object `measured` containers are rejected
with a nonzero report exit instead of a fabricated decision.

Smallest honest design choice: compare against the immutable run-local config,
not a current config selected by policy name, and leave all untested metadata
unchecked. Alternatives deferred: a physics-check registry that could grant
`verified`, physical checks for metadata, and a broader units/normalisation
verification ledger. No new simulation input or physical value was introduced.
