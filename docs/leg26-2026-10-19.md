# LEG 26: declared scope and rule identity must reach the analytic verdict

Date: 2026-10-19. Branch: `leg26-scope-and-rule-identity`. Base: `origin/main` at `9311b96`
(the registration commit for LEG 26 and LEG 27). Resource tag: `neither` — CPU only, no
`./tools/run.sh`, no GPU, no lock, no `runs/` row.

This is a **test leg**. Its write set is `checks/test_leg26_scope_and_rule_identity.py` and this
document. No implementation file was edited, in this repository or in the solver fork.

## 1. Why the leg exists

`plan.md` § LEG 26 registers two defects in the verification tooling, reported by a read-only sweep
against `main` at `c3c047d`:

1. **Scope is an annotation, not a verdict input.** `evaluate_analytic_cases` computes the status
   from finiteness and the tolerance alone (`src/analytic_cases.py:316`; the scalar path does the
   same at `:232`). The config field `scope_match` is copied onto the result row (`:240`, `:324`)
   but never enters the condition, and no consumer reads it. An out-of-scope case whose numbers
   happen to agree is therefore stamped `passed`, and then labelled `verified`.
2. **Rule identity is used as case identity.** `label_analytic_cases` builds
   `rows = {row['id']: row for row in evaluate_analytic_cases(...)}` (`:335`), keyed on the rule
   id alone. When two cases share one rule id — already true in
   `configs/leg4-convergence-ladder.json`, which reuses `V1-fresnel` for
   `ladder-interface-ppw20/40/80/160` — the last evaluated row wins. The labelling loop
   (`:344-374`) then reads `status`, `tolerance` and `basis` from that row without checking
   `case_id`, so a failing case can have its remaining points labelled `verified` with its
   passing sibling's tolerance and basis.

Both defects were **reproduced before any test was written**, with in-memory synthetic readouts and
the real `src/analytic_cases.py`. The reproductions are recorded in §2. Nothing in `runs/`,
`scratch/` or an archived run was read.

## 2. Independent reproduction of the two defects

The reproduction script lived in `/tmp`, not in the tree. It imported only `analytic_cases` and
used the `fresnel` law the module itself recomputes (`index = 3.5`, wavelengths
`[1.2, 1.35, 1.5]` micrometres).

### 2.1 Scope does not reach the status

One in-memory case whose measured `R` and `T` equal the recomputed Fresnel values exactly, declared
with `scope_match: false` and tolerance `0.01`:

```
status: passed scope: False error: 0.0
verified labels: 6
```

The same fixture on the scalar path (`V1-grating-zero-order`, law `film-tp`) produced `passed` and
two `verified` fields. Confirmed lines: `src/analytic_cases.py:316` (curve path) and
`src/analytic_cases.py:232` (scalar path). A search over `src/`, `tools/`, `checks/` and `configs/`
found no consumer that reads the row's `scope` field; the only mention outside `analytic_cases.py`
is prose in `tools/report.py:46`.

### 2.2 Shared rule id shares the verdict and the sibling's numbers

Two in-memory cases, both declared with rule id `V1-fresnel`:

- case `a`: `T[1]` shifted by `+0.03`, declared tolerance `0.001` — fails on its own;
- case `b`: exact values, declared tolerance `0.05` — passes on its own.

With `a` declared first, `evaluate_analytic_cases` returns two rows in order
`(id, case_id, status, tolerance) = (V1-fresnel, a, failed, 0.001)`,
`(V1-fresnel, b, passed, 0.05)`. The dict at `:335` keeps only `b`. The labelling loop then iterates
the `a` entry, reads `b`'s `passed` row, and labels **all six of case `a`'s points** `verified`,
quoting `<= 0.05` and `Basis: test basis for case b` in the reason. Swapping the declaration order
puts `a`'s failed row last, so nothing is labelled at all — including case `b`'s exact points.

Confirmed lines: `src/analytic_cases.py:335` (row keying) and `:345-362` (status, tolerance and
basis read from the collapsed row; the `case_id` is carried only into the prose).

The sweep's own example had five wavelength points, so it saw "the other four" labelled. Our
fixture has three wavelengths and two curves per case, i.e. six points per case, so the same
mechanism labels five or six of them depending on the sibling's tolerance. This is a difference in
fixture shape, not in the defect.

## 3. The tests

File: `checks/test_leg26_scope_and_rule_identity.py`. It follows the shape of
`checks/test_analytic_cases.py`: `sys.path.insert` of `src/`, `import analytic_cases`, synthetic
readouts and headline lists built in memory, no simulation import.

All measured data are synthetic and in memory. The analytic targets are recomputed by
`analytic_cases._law_values` / `analytic_cases.scalar_law_points`; no stored target is read. The
scalar fixture reuses the published grating fixture values already present in
`checks/test_analytic_cases.py` (`index 2.0`, `thickness 0.6` micrometres, `wavelength 1.54925`
micrometres, angles `8.5` and `8.9002` degrees) and only recomputes its law.

There are exactly four test methods, one per pre-declared requirement:

1. `ScopeReachesTheVerdict.test_an_out_of_scope_case_is_neither_passed_nor_verified` — an
   out-of-scope exact match must not be `passed`, and must not be labelled `verified` afterwards.
   Covers both the curve path and the scalar path.
2. `SharedRuleIdDoesNotShareAVerdict.test_a_failing_case_is_not_labelled_by_its_passing_sibling` —
   with one shared rule id, the failing case's points must carry no `verified` label, in both
   declaration orders; the set of labelled points must not depend on the order.
3. `LabelReasonsCiteTheirOwnCase.test_a_labels_reason_quotes_its_own_case_not_its_sibling` — every
   `verified` label's reason must quote the basis and tolerance declared for the case whose path it
   is on, never its sibling's.
4. `NegativeControl.test_an_in_scope_matching_case_is_still_verified` — an in-scope exact case must
   stay `verified`. The plain single-case control is asserted, then the same case with a failing
   sibling that shares its rule id, in both declaration orders. A fix that simply disables
   labelling cannot pass.

Test 4 is deliberately more than the plain control: the plain control passes on today's `main`
(and therefore could not be one of the four failing tests the registration requires), while the
same case alongside a failing sibling sharing its rule id fails today in the `passing first` order,
because the collapsed row is the failing one. This keeps the negative control both meaningful and
failing on `main`, as `plan.md` requires.

## 6. What the eventual implementation leg should change (report only, not applied)

This section is guidance for the separate implementation leg; nothing here was written into
`src/`.

1. **Make an explicit out-of-scope declaration block a pass, in both status computations.** The
   condition at `:316` and the scalar condition at `:232` should require the case to be in scope
   in addition to `finite and worst_error <= tolerance`. The existing configs use `true` or the
   string `"matched"`, so the predicate must treat both as in scope and an explicit `false` as out
   of scope. The test accepts any non-`passed` outcome, so the implementation may choose `failed`
   or a dedicated status, provided the existing in-scope cases keep their current verdicts.
2. **Key the labelling rows by `(id, case_id)`.** At `:335` the dict must not lose the row identity
   that `evaluate_analytic_cases` already returns; at `:345-347` the lookup must use both fields.
   Falling back to the rule id alone when the pair is absent would reintroduce the defect.
3. **Keep labelling in-scope passing cases.** Test 4 fails both a fix that only disables labels and
   a fix that keys conservatively by first-seen rule id, because the exact-match sibling must stay
   `verified` in both declaration orders.
4. **Do not change the labelling of a failing case.** The existing rule ("a failing case verifies
   nothing") is correct and is preserved; after the row keying is fixed, case `a` simply has no
   labels.

Sanity check of satisfiability, performed on a **throwaway copy** at `/tmp/opencode/fixed`

the real test module loaded against it:
