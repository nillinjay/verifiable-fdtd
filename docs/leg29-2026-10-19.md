## 2. Defect 1: `scope_match` did not gate the status

**Before.** Both computations decided `passed` from the tolerance alone:

- scalar path, `_evaluate_scalar`, `src/analytic_cases.py:232`
- curve path, `evaluate_analytic_cases`, `src/analytic_cases.py:316`

`scope_match` was only copied onto the returned row (`:240`, `:324`), and nothing downstream read
it. A configuration that explicitly declared a case out of scope could still be stamped `passed`
on an exact numeric match, and `label_analytic_cases` then promoted its points to `verified`.

**After.** Both paths compute the scope first and require it for a pass
(`src/analytic_cases.py:232-234` for the scalar path, `:321-323` for the curve path):

```python
in_scope = entry.get('scope_match') is not False
status = 'passed' if finite and in_scope and worst_error <= tolerance else (
    'out-of-scope' if not in_scope else 'failed')
```

An explicitly out-of-scope case receives the dedicated status `out-of-scope`, which is neither
`passed` nor a numeric `failed`. The frozen tests accept any non-`passed` value; LEG 26's own
report explicitly left that choice open (`docs/leg26-2026-10-19.md` §6.1). The dedicated status is
preferred because the numeric comparison did not fail — the case is refused for its declared
scope, and recording it as a numeric failure would misstate why. Every consumer in the tree tests
`status == 'passed'` or `status != 'passed'`, so a scope refusal remains fail-closed everywhere:
`leg3_analytic.py:85`, `leg14_slab.py:165`, `leg14_grating.py:142`, and the labelling loop itself.

The predicate is `is not False`, not truthiness. This is required for compatibility: the existing
helper `checks/test_analytic_cases.py:config_for` omits `scope_match` entirely and expects
`passed` on exact curves, and the configs written before the field existed also omit it. A missing
field therefore means "no out-of-scope declaration", i.e. in scope. The existing declarations use
JSON `true` and the string `"matched"`, both of which remain truthy and in scope. Only an explicit
JSON/Python `false` blocks a pass.

## 3. Defect 2: one rule id was treated as one case

**Before.** `label_analytic_cases` built `rows = {row['id']: row …}`
(`src/analytic_cases.py:335`) and looked a declared entry up by `entry['id']` alone
(`:345-347`). When two cases share a rule id — already live in
`configs/leg4-convergence-ladder.json`, which reuses `V1-fresnel` across four ppw cases and one
time-step case — the last evaluated row won. The labelling loop then took `status`, `tolerance`
and `basis` from that row without checking `case_id`, so a failing case could be labelled
`verified` with its passing sibling's tolerance and basis. The failure was order-dependent: which
case was labelled correctly depended on declaration order.

**After.** A result row is identified by the pair that `evaluate_analytic_cases` already returns:

```python
rows = {(row['id'], row['case_id']): row
        for row in evaluate_analytic_cases(readout, config)}
```

and the labelling loop looks up that pair (`src/analytic_cases.py:345-346`, `:356-360`). There is
**no** fallback to the rule id alone when the pair is absent, because the fallback would recreate
the collapse. A declared entry with no evaluated row is skipped, as before. Each case's own
`status`, `tolerance` and `basis` now decide its own labels, independent of declaration order.

## 5. Intent inferred from the frozen tests, and how it was checked

- **Which value means "out of scope".** The fixtures pass the Python boolean `False`; the live
  configs pass `True` or the string `"matched"`. The predicate was therefore read as "explicitly
  false blocks a pass; absent, true or a descriptive string do not". This reading was checked two
  ways: the frozen tests pass, and the pre-existing `checks/test_analytic_cases.py` suite (whose
  helper omits the field) stays green.
- **Whether a dedicated status is allowed.** The frozen tests only assert
  `status != 'passed'`. LEG 26's report §6.1 explicitly permits `failed` or a dedicated status, so
  `out-of-scope` was chosen to keep the two meanings distinct.
- **Whether the negative control requires true labelling rather than a vacuous pass.** Test 4
  compares verified paths to the in-scope case's full path set, so labelling had to remain intact;
  it was not enough to suppress all labels.
- **Whether an id-only fallback is acceptable.** LEG 26's report §6.2 says a fallback "would
  reintroduce the defect"; the implementation deliberately has none.
