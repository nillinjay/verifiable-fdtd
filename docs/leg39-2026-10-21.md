# LEG 39 — the harness runs from a fresh clone, not only from a machine that already holds the state (2026-10-21)

**Outcome in one line.** The exported tree ran **397 tests to exit `0`** after adding only the solver
link (plus the untracked Python environment the exporter deliberately removes); the working repository
stayed at **397 tests, `OK`**, with the same test-id set on both trees. No test was skipped, deferred or
deleted to get there.

## The finding, reproduced before the fix

The project now has a public exporter (`tools/export_public.sh`). A fresh copy of that export has the
tracked files but not the untracked machine state. Copying it, linking the solver, and running its own
suite failed exactly as registered:

```text
$ tools/export_public.sh --dest /tmp/leg39-export
$ cd /tmp/leg39-export
$ tools/bootstrap_solver.sh "$SOLVER_FORK"
$ "$SOLVER_ENV/bin/python" -m unittest discover -s checks
...
Ran 397 tests in 3.046s
FAILED (failures=4, errors=32, skipped=15)
```

Two checks read state a clone does not have, and they failed in two different ways:

1. **32 errors** from `checks/test_leg21_o6_assessment.py`, whose `solver_root()` shelled out to
   `. env/refs.env && printf "%s" "$SOLVER_FORK"` with `check=True`. `env/refs.env` is untracked by
   design (`AGENTS.md`), so every citation resolution raised before it could look at the solver. The
   clone *does* have `src/torchfdtd`, created by `tools/bootstrap_solver.sh`; that link is the correct
   source of truth.
2. **4 failures** in `checks/test_preflight_reference_policy.py`. `checks/pre_environment.py` checked
   the frozen upstream baseline before it reached the reference-contract gate. A clone has no
   `src/torchfdtd_upstream` link, so the subprocess died with a `CalledProcessError` traceback and exit
   `1` where the tests require the declared refusal and exit `65`.

Both are one defect class: a harness precondition that belongs to the *machine* was written as a
precondition of the *suite*.

## The changes

### `checks/test_leg21_o6_assessment.py`

`solver_root()` (`:26-43`) now resolves in this order:

1. `src/torchfdtd`, if it is a directory (the link `tools/bootstrap_solver.sh` creates);
2. `$SOLVER_FORK`, only as a fallback when that link is missing;
3. otherwise `AssertionError` naming **both** candidates and the command that creates the link.

Nothing downstream changed: `pinned_lines()` (`:46-55`) still runs `git -C <solver> show
ad436c9:<path>` and still has no working-tree fallback, line search or solver import. The pin, the
citation validator and both negative controls are untouched.

### `checks/pre_environment.py`

1. **The reference-contract gate now runs before any solver or provenance lookup** (`:119-148`). It
   answers from the config alone, so it is reachable on a clone. The four `LEG 28` tests see the
   refusal they assert: exit `65`, the message naming the missing module, the requiring field and "no
   simulation was run".
2. **`check_upstream()` is a declared refusal when the baseline is absent** (`:52-86`) instead of a
   `CalledProcessError` traceback. `required=True` (the default) prints the refusal and exits `65`; it
   says what is missing, which pin it needs, and that nothing ran. A **moved or dirty baseline that is
   present is still a hard failure** — those two asserts are unchanged.
3. **A read-only audit may proceed without the baseline** (`:150-158`). `kind == 'audit'` does not read
   the frozen baseline, so its absence is printed to stderr and recorded as `upstream=absent` in the
   summary line (`:167`, `:176-177`). A run that measures something, and `PARITY_SOLVER_ROLE=upstream`
   (which exists to reproduce pre-v2.0 evidence), still take the exit-65 refusal.
4. **`check_fork()` is also a declared refusal when the fork link is absent** (`:96-108`), rather than
   a traceback, so a genuine run without a solver exits `65` with instructions.

One implementation detail is load-bearing and was found by the full suite, not by inspection: the
availability of the upstream baseline must be decided by **calling `git` and catching its failure**, not
by pre-checking `Path.is_dir()`. `checks/test_driver_contracts.py` drives `pre_environment.py` with a
mocked `subprocess.check_output` and paths that need not exist; a path pre-check bypassed the mock and
broke four CPU gate contracts. The first commit did exactly that and the exported suite reported
`failures=2, errors=2`; the fix is the second commit in this leg.

## What still depends on something outside the repository

- **The linked solver must carry commit `ad436c9` in its object database.** That is the commit the
  `LEG 21` assessment cites, and the test deliberately reads Git objects, not the working tree. The
  fork checkout has it; the frozen upstream checkout (`ebcc0f7`) does **not**, so linking only
  `src/torchfdtd_upstream` would make the citation test fail. That is the evidence contract working as
  intended, not a machine-state leak, but a public user must link the fork (as the README says) rather
  than a shallow or upstream-only clone.
- **The Python environment** (`.venv`) is not published and must be created by the reader
  (`README.md` install section). This leg supplies none.
- **Archived run payloads** are untracked; a tree without them skips the declared `LEG 27`/`LEG 18`
  guards. The acceptance treats those as declared gaps, not as passes.
- `tools/export_public.sh` printed `WARNING: no env/scrub-paths.txt` in this worktree because the scrub
  table is itself untracked here. The export still removed `$HOME`; that warning predates this leg and
  is outside its write set.
