## The tolerance is now earned, not borrowed

Criterion C6. Leg 3 had to declare its `0.01` absolute threshold `INHERITED`. This leg measures
what that threshold actually costs:

| ladder | error at the registered `ppw` 40 | margin against the inherited `0.01` |
|---|---|---|
| `V3-interface` | `1.092e-03` | `9.16x` inside |
| `V3-slab` | `8.437e-03` | `1.19x` inside |

**And the coarse rung is not inside it.** At `ppw` 20 the slab's error is `3.412e-02`, which is
`3.4` times *worse* than the inherited threshold. So the honest statement of that threshold is:
`0.01` absolute holds for these cases at `ppw >= 40`, not everywhere. Leg 3's tolerance was
therefore a resolution-specific floor all along, and the ladder is what shows it.

## The coincidence guard

Criterion C4 requires the guard to be executable and demonstrated. It is implemented in
`src/convergence.py` as `coincidence()` and `apply_coincidence_guard()`, wired into
`tools/report.py`, and covered by six unit tests.

Control: `./.venv/bin/python src/leg4_ladder.py runs/20261018T062043Z-269360 --guard-control`
perturbs the finest rung in memory so that it lands outside tolerance while the coarse rung stays
inside it. Result:

```
V3-interface status=stopped-non-monotone monotone=False coincidence=True
               errors=[0.004411, 0.001092, 0.000272, 0.499969]
verified labels on that ladder: 147 before the guard, 0 after it
Source run files were not modified.
```

Exit `0`, meaning the guard fired and removed every `verified` label on that ladder. Full output:
`scratch/leg4-guard-control.txt`.

> **Later correction, 2026-10-20 (LEG 33).** The block above is preserved verbatim on purpose: it is
> what the tool printed on 2026-10-18, and a historical measurement is not rewritten to agree with
> later code. Re-running the same control after LEG 29's row-keying fix (merged 2026-10-19) now
> prints **`126`** `verified` labels before the guard, and `0` after. The fix keys analytic labels on
> `(rule id, case_id)` instead of the rule id alone, so the perturbed finest interface rung no longer
> inherits `21` `R` labels from a passing case. The original `147` stands as the result at the time;
> see `docs/leg33-2026-10-20.md` for the full correction record.

**A limitation, stated rather than hidden.** With this tolerance a *monotone* ladder cannot produce
a coincidence: if the fine rungs keep improving, and the coarse rung is already inside `0.01`, then
every later rung is inside it too. Coincidence therefore appears only when the fine rungs behave
worse than the coarse one, which the monotonicity gate already stops. The guard is still the right
rule, because it is what forbids `verified` in exactly that case; but it is not the first line of
defence here — the monotonicity gate is.

## What could not be done

1. **No continuum extrapolation is claimed**, even though the fit supports one. The fit is offered
   as evidence of the order, not as a corrected value. A Richardson extrapolation of the observable
   would need its own registration, its own criteria, and its own validation on a second quantity.
2. **Two mesh rungs are still one knob.** This leg varies the mesh on two analytic cases only. The
   guided fixtures (N8, G8) have no exact answer, so their convergence is not measured here and
   their numbers stay `consistent`.
3. **`V5` (the units and normalisation ledger) is still open.** It is the last leg of the `V` block
   as the owner sequenced it.
4. The `extrapolation: supported` rule is a **declared heuristic** (fit residual at most 10 percent
   of the fitted order), not a physics statement. It is stated here so a reader can disagree with it
   on the record.
