# LEG 40 — an MCP server for the platform, judged by the process exit status

Date: 2026-10-21. Branch: `leg40-mcp-server` (the commit that carries this file).
Registration: `plan.md`, section **LEG 40**.

## 1. What this leg delivers

A Python package `mcp_server/` and a `pyproject.toml` entry point
`torchfdtd-platform-mcp`. The server speaks MCP over **stdio** by default and over the
**streamable HTTP** transport when `--http` is given. It exposes exactly six tools:

| tool | signature | returns |
|---|---|---|
| `list_configs` | `list_configs()` | `{ok, configs[], unpaired_configs[], source}`; each pair is `{config, driver, driver_exists, purpose}` |
| `describe_run` | `describe_run(config)` | `{ok, config, driver, driver_source, driver_exists, solver{role,root,available,python_package_seen}, criteria[], criteria_text, criteria_source, criteria_note, validation, command, argv}` |
| `validate_config` | `validate_config(config)` | `{ok, errors[], config, validator, environment_stubbed, note}` |
| `submit_run` | `submit_run(config, dry_run=True)` | dry run: `{ok, dry_run, executed, kind, command, argv, preflight, ...}`; real run: `{ok, exit_status, run_id, ledger_row, stderr_tail, kind, executed, process_started, tail_source, stdout_tail, meaning, ...}` |
| `read_ledger` | `read_ledger(limit=20)` | `{ok, rows[], count, total, ledger}`; rows are the last N, in file order |
| `explain_exit` | `explain_exit(code)` | `{ok, known, code, kind, meaning, source}`; unknown codes are `known: false` |

The design rule is the one the owner asked for: **the model proposes, the harness
disposes.** No tool calls a model, imports a model SDK, or decides acceptance.
`ok` is derived from the process exit status. Only `0` is success. `57` is a lawful
finding and is reported as `ok: false, kind: "finding"`.

## 2. The three properties that decide whether this is any good

### 2.1 `submit_run` never claims success when the run said otherwise

`submit_run(dry_run=False)` executes only `tools/run.sh` (no shell, no other program),
with the config and the driver as its two arguments. It returns the launcher's exit
status unchanged. `ok` is `exit_status == 0`; `kind` comes from the shared vocabulary
in `README.md`. The negative control is section 4.3.

`stderr_tail` is the last 20 lines of stderr. The launcher writes its progress and the
driver's own output to stdout, so when stderr is empty the tool falls back to the stdout
tail and says so in `tail_source` (`"stderr"` or `"stdout"`). The payload still carries
the required key, and a reader can tell which stream it came from.

### 2.2 The server starts without the solver

No module in `mcp_server/` imports `torchfdtd`. A run request checks for the solver
directory and refuses with `kind: "solver_unavailable"` before starting a process. The
solver itself is imported by `tools/run.sh` in its own process, never by the server.
Section 4.4 proves the server starts, lists tools, validates a config and refuses a run
with the solver link absent.

### 2.3 Validation is the existing code, not a new copy

`validate_config` executes `checks/pre_environment.py` — the project's existing config
gate — with `runpy`, and returns what that gate says. It does not restate the rules.
The gate also probes the machine (upstream/fork git state, CUDA presence). Those probes
are supplied with inert answers because a *config* validation must not read the machine;
the config assertions (`task`, `kind`, the reference-contract branch) are the real ones.
The file `checks/pre_environment.py` is unchanged. On an actual run, `tools/run.sh`
runs the same gate unstubbed, so solver provenance and GPU availability are still
enforced where they belong.

## 3. Package and launch paths

```
mcp_server/__init__.py      package marker; no solver import
mcp_server/cli.py           argparse: --http, --host, --port; stdio by default
mcp_server/server.py        the six FastMCP tools
mcp_server/platform.py      list/describe/submit/ledger/exit logic
mcp_server/validation.py    the existing gate, called in-process
mcp_server/plan.py          the leg's criteria, quoted from plan.md
mcp_server/paths.py         project root and config/driver resolution
mcp_server/exits.py         the shared exit vocabulary
mcptests/                   the acceptance tests and fixtures
pyproject.toml              packages mcp_server only; entry point
```

`pyproject.toml` declares the entry point

```
torchfdtd-platform-mcp = mcp_server.cli:main
```

and the dependency `mcp>=1.0,<2`. There is no model SDK dependency. The `mcp` extra is
declared as well, so both `pip install -e .` and `pip install -e .[mcp]` are meaningful.

The HTTP transport is enabled by `--http`. It binds the MCP streamable-HTTP endpoint at
`/mcp`:

```bash
torchfdtd-platform-mcp --http --port 8787                 # loopback only
torchfdtd-platform-mcp --http --host 0.0.0.0 --port 8787  # reachable by a remote client
```

A remote client (for example a hosted MCP client that cannot spawn a local process)
configures the URL `http://<host>:8787/mcp`. The default host is loopback; remote use
requires an explicit `--host`, because the server executes a run on request and has no
authentication layer of its own.

## 4. Acceptance evidence

All commands were run from the repository root with the project interpreter
`.venv/bin/python`. `python` is not on `PATH` in this non-activated shell; the venv
interpreter is the same interpreter the project pins. No test used a GPU and no test
opened a socket.

### 4.1 A1 — an in-process MCP client over stdio exercises all six tools

Command:

```bash
.venv/bin/python -m unittest discover -s mcptests
```

Observed output:

```
......
----------------------------------------------------------------------
Ran 6 tests in 2.564s

OK
```

Exit status `0`. The client is `mcp.ClientSession` over `mcp.client.stdio.stdio_client`;
the server is spawned as `sys.executable -m mcp_server`. The test lists the tools and
asserts the set is exactly the six names, then calls all six:

- `list_configs` returned 32 ledger-backed config/driver pairs; every config and driver
  it names exists on disk, and every pair carries a non-empty purpose taken from the
  config's `task`.
- `describe_run("configs/leg24-graded-check.json")` returned driver
  `src/leg24_graded_modal.py`, solver role `fork`, five criteria, and
  `criteria_source: "plan.md:2385"`.
- `validate_config("configs/selftest-spine.json")` returned `ok: true`.
- `validate_config("mcptests/fixtures/invalid-config.json")` returned `ok: false` with
  a named error.
- `submit_run("configs/selftest-spine.json", dry_run=True)` returned the exact command,
  `argv[0]` ending in `tools/run.sh`, `dry_run: true`, `executed: false`.
- `read_ledger(limit=3)` returned the last three ledger rows and the test compared them
  to the last three lines of `runs/ledger.jsonl`; they are identical in order and values.
- `explain_exit(57)` returned `known: true, ok: false, kind: "finding"`;
  `explain_exit(991)` returned `known: false, kind: "unknown"`.

### 4.2 A2 — an invalid config is a structured refusal and starts no process

Fixture: `mcptests/fixtures/invalid-config.json` is `{"kind": "audit"}`. It has no
`task`, which the project's own gate refuses.

The test runs against an isolated project root and calls
`submit_run(dry_run=False)`. The observed payload:

```json
{
  "ok": false,
  "dry_run": false,
  "executed": false,
  "kind": "invalid_config",
  "errors": ["Every run needs a step number in task"],
  "config": "configs/invalid-config.json",
  "validation": {
    "ok": false,
    "errors": ["Every run needs a step number in task"],
    "validator": "checks/pre_environment.py",
    "environment_stubbed": true
  },
  "exit_status": null,
  "run_id": null,
  "ledger_row": null,
  "stderr_tail": ""
}
```

The refusal is distinguishable from success by the payload itself (`ok: false`,
`kind: "invalid_config"`, `executed: false`, a non-empty `errors` list), not by a log
line. The test also asserts that the isolated root's `runs/` directory does not exist
after the call: no run directory, no ledger row, no process.

### 4.3 A3 — a driver that exits 57 is a finding, not a success

Fixture: `mcptests/fixtures/exit57.py` prints one line and exits `57`.
`mcptests/fixtures/exit57.json` is a `kind: "audit"` config naming that driver. The test
builds a minimal isolated project root, copies the driver to `src/exit57.py` (the
launcher snapshots `src/`, `checks/`, `tools/` and `configs/`), creates a solver-shaped
git repository at `src/torchfdtd`, and then calls
`submit_run("configs/exit57.json", dry_run=False)` through the real `tools/run.sh`.

Observed payload (the run id below is from the reproduction that produced this excerpt;
the test generates a fresh one each time):

```json
{
  "ok": false,
  "exit_status": 57,
  "kind": "finding",
  "executed": true,
  "process_started": true,
  "run_id": "20261021T113200Z-392423",
  "ledger_row": {
    "run_id": "20261021T113200Z-392423",
    "status": "failed:exit=57",
    "exit_code": 57,
    "config": "configs/exit57.json",
    "script": "src/exit57.py",
    "solver_role": "fork",
    "solver_dirty_lines": 0
  },
  "tail_source": "stdout",
  "stderr_tail": "[run.sh] run_id=20261021T113200Z-392423\n...\nleg40-fixture: measured quantity violates its pre-declared threshold (finding)\n[run.sh] exit=57 status=failed:exit=57 run_dir=...",
  "meaning": "the measured quantity violates its threshold -- a finding, not a crash"
}
```

`exit_status` is exactly `57`; `ok` is `false`; `kind` is `"finding"`. A tool that
returned `ok: true` here would be the defect this project exists to catch.

The isolated root's ledger contains exactly one row, with `exit_code: 57`. The tracked
`runs/ledger.jsonl` of this repository was not touched by the test.

### 4.4 A4 — the server starts without the solver and refuses cleanly

The test builds the same isolated root but does **not** create `src/torchfdtd`. It starts
the server over stdio and calls `list_configs`, `validate_config` and
`submit_run(dry_run=False)`.

Observed:

- the server started and answered `list_configs` with `ok: true`;
- `validate_config` returned `ok: true` for the fixture config (the gate's config
  assertions pass; its machine probes are stubbed);
- `submit_run` returned
  `{ok: false, kind: "solver_unavailable", executed: false,
  errors: ["solver is unavailable at src/torchfdtd; run tools/bootstrap_solver.sh first"]}`;
- `src/torchfdtd` is absent, the isolated `runs/` directory does not exist, and the
  server's stderr captured by the test is empty — no traceback.

The package's import path is also tested: no module in `mcp_server/` contains
`import torchfdtd`.

### 4.5 A5 — the existing suite is untouched

Command:

```bash
.venv/bin/python -m unittest discover -s checks
```

Observed in this worktree:

```
Ran 397 tests in 3.697s

OK (skipped=15)
```

Exit status `0`. The test count is the pre-declared `397` and the result is `OK`. The

is run in the main checkout that holds the archived run directories, the registered
`3` skip count is the expected one; the test count and exit status are unchanged here.

## 5. HTTP transport evidence

`--http` was smoke-tested directly, not as part of `mcptests` (the tests use stdio only,
and the acceptance forbids network in tests). The server was started with

```bash
.venv/bin/python -m mcp_server --http --port 8799
```

and a raw MCP `initialize` request was posted to `http://127.0.0.1:8799/mcp` with
`Content-Type: application/json` and `Accept: application/json, text/event-stream`.
The response was `HTTP/1.1 200 OK`, `content-type: text/event-stream`, an
`mcp-session-id` header, and a JSON-RPC result naming
`torchfdtd-platform-mcp`. This proves the transport is mounted; it is not a full
hosted-client round trip.

## 6. Stop conditions, checked

1. **No model SDK dependency.** `mcptests` scans every `mcp_server/*.py` import for
   `openai`, `anthropic`, `litellm`, `google.generativeai` and `cohere`; none is
   present. `pyproject.toml` depends only on `mcp`.
2. **A tool may execute only `tools/run.sh`.** `submit_run` is the only tool that
   starts a process, and it calls `[<root>/tools/run.sh, <config>, <driver>]` with
   `shell=False`. `validate_config` runs the existing gate in-process with its machine
   probes stubbed; it starts nothing.
3. **Do not weaken a validator.** `checks/pre_environment.py` is unchanged. The
   validation tool uses the real config assertions; the stubbing is limited to the
   machine probes and is reported in every validation payload.
4. **No network in any test.** `mcptests` uses stdio pipes only. The loopback HTTP
   check in section 5 is a manual smoke test, not a unittest.

## 7. Packaging

`uv build --wheel` produced `torchfdtd_platform_mcp-0.1.0-py3-none-any.whl` with the
entry point

```
[console_scripts]
```

and `Requires-Dist: mcp<2,>=1.0`. The wheel contains `mcp_server/` only; `mcptests/`

The editable install could not be completed in this environment: the shared `.venv`

launch the package with `python -m mcp_server`, which exercises the same module and
`main()`.

## 8. What could not be determined

- **A5's skip count in this worktree.** It is 15, not 3, because the archived run
  directories are not present here. The test count and exit status match; the skip
  difference is environmental and is explained in section 4.5.
- **A hosted-client round trip over HTTP.** The transport was smoke-tested with a raw
  `initialize` request on loopback. A real hosted client was not available, and the
  tests deliberately do not open a socket.
- **Editable installation end to end.** The shared venv is read-only and lacks `pip`.
  The wheel and its entry point were built and inspected, but
  `torchfdtd-platform-mcp` was not installed into this venv.
- **What `validate_config` does not certify.** It does not certify that the solver
  checkout is present, clean or at the pinned commit, and it does not certify GPU
  availability. Those are the launcher's pre-flight gate, which runs unstubbed on an
  actual `tools/run.sh` execution. `validate_config` answers a narrower question: is
  this config acceptable to the project's own config gate?
- **Config/driver pairs with no ledger row.** `list_configs` reports only pairs the
  ledger records; a config that has never run and carries no `driver` field appears
  under `unpaired_configs` with a reason. `configs/leg21-o6-assessment.json` is not a
  run config (it has no `task`/`kind`), so it is not listed at all.
