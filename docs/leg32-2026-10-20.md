# LEG 32 — the leg-15 diagnostics driver must refuse when its criteria fail

Date: 2026-10-20. Branch `leg32-leg15-exit-contract`, base `origin/main` at `42459dd`
(the merge of LEG 28). This is a **test leg**: the only files written are
`checks/test_leg15_exit_contract.py` and this document. `src/leg15_closure.py` is untouched.
CPU only: no `./tools/run.sh`, no GPU, no resource lock, no archived run data, and no import of
the solver module `torchfdtd`. Every readout in the tests is a dictionary built in memory.

## The defect

`src/leg15_closure.py:137` defines `main()`. Near its end it copies the config's pre-declared
hypotheses and negative control into the readout:

```
src/leg15_closure.py:204      hypotheses=config['hypotheses'],
src/leg15_closure.py:205      negative_control=config['negative_control'], cases=rows, units=config['units'])
```

and then returns:

```
src/leg15_closure.py:209      return 0
```

That is the **only** `return` in `main()`. Nothing compares the readout with the hypotheses or
with the negative control. The test that was supposed to hold those criteria,
`checks/test_leg15_closure.py`, skips whenever the archived leg-12/leg-15 runs are absent
(`MEASURED is None`, `leg15_results()` empty), which is the usual state of an acceptance
workspace. The chain "driver exits `0` → ledger records `completed`" therefore never consults a
criterion. A lost or vacuous negative control changes nothing.

## The pinned contract

`plan.md` section LEG 32 pins a pure function in the driver:

```
verdict_exit(readout: dict) -> int
```

| return | meaning |
|---|---|
| `0` | every pre-declared criterion holds, **and** the negative control is present, marked as having failed in the required direction, and carries evidence that it ran |
| `61` | a pre-declared criterion is violated; the message names which one |
| `62` | the negative control is missing, vacuous, or passed in the wrong direction |
| `63` | the readout carries no pre-declared criteria block at all |

The exit codes are fixed by the plan. The exact **readout shape** is not written in the plan, so
this test file pins it. The shape follows existing project conventions:

- `criteria` is a name → bool map. Legs 16 and 19 already store their gates this way
  (`src/leg16_tooth_convergence.py:264`, `src/leg19_admission.py:229`). The names used here are the
  six criteria of leg 15's own registration (`plan.md` section LEG 15: C1–C6).
- `negative_control` is the block the driver already copies from the config. The test adds the
  three facts the contract requires: `status` (`'failed-as-required'` when the control failed in the
  direction the readout expects), `executed` (it ran), and `observed` (the measured evidence).

A passing readout built by the tests:

```python
{
    'policy': 'leg15-closure-v1',
    'status': 'completed',
    'simulation_executed': True,
    'criteria': {'C1': True, 'C2': True, 'C3': True, 'C4': True, 'C5': True, 'C6': True},
    'negative_control': {
        'case': 'lossy-control',
        'expect': 'energy_residual at least 1e4 times the effect under test '
                  '(leg 12 measured 3.4032e-01)',
        'status': 'failed-as-required',
        'executed': True,
        'observed': {'energy_residual': 0.34032},
    },
    'cases': [
        {'id': 'baseline', 'energy_residual': 7.50792e-07},
        {'id': 'lossy-control', 'energy_residual': 0.34032},
    ],
}
```

The numbers are leg 15's recorded ones: the baseline reproduces leg 12's `7.50792e-07` and the
lossy control's `3.4032e-01` is the value in `configs/leg15-closure.json`. They are literals in the
test, not read from `runs/`.

### Importing the driver without importing the solver

`src/leg15_closure.py` starts with `from parity import *`, and `parity` imports `torchfdtd`. The
stop conditions forbid importing `src/torchfdtd`, and `src/torchfdtd` is a machine-local link that
is absent on many machines. The tests therefore import the driver under a stub `parity` module
(`checks/test_leg15_exit_contract.py`, `driver()`), which supplies only `np`. `verdict_exit` has
to be pure, so it must not need the solver. The only torchfdtd-related entry in `sys.modules`
during the run is `__editable___torchfdtd_1_1_4_finder`, the venv's editable-install finder, which
the interpreter loads at startup whether or not this test runs; the `torchfdtd` module itself is
never imported (`'torchfdtd' in sys.modules` is false).

### The message requirement of test 2

The pinned signature returns an `int` and nothing else, so it has no message channel. The only
observable message is the process output. Test 2 therefore runs `verdict_exit` with
`contextlib.redirect_stdout` and `redirect_stderr` to one buffer and requires the name `C1` to
appear there in addition to the return value `61`. An implementation that returns `61` silently
fails test 2: a bare status code does not tell the reader which gate failed. This is the one place
where the test had to choose a channel the plan did not name; the choice is stated here so the
implementation leg can satisfy it deliberately.

## What could not be tested, and why

- **Which criteria the implementation actually computes, and whether they are the right ones.**
  The contract is about the exit status given a criteria block. The tests require a `criteria` map
  of booleans and exercise all four outcomes, but they do not, and cannot, decide whether `C1`–`C6`
  are computed correctly from the run rows: that computation needs the archived run data and is
  the implementation leg's job. A `verdict_exit` that trusts a wrong `criteria` block would pass
  these tests.
- **The driver's `main()` integration.** The tests import the pure function directly. They do not
  run `main()`, because that needs `./tools/run.sh`, the GPU and archived data, all forbidden here.
  The implementation leg must still call `verdict_exit(readout)` and return its value instead of
  the unconditional `return 0` at `src/leg15_closure.py:209`; this test file cannot observe whether
  it does.
- **The message channel.** As stated above, the plan says a message must name the violated
  criterion but the pinned signature has no message parameter or return value. Test 2 pins
  stdout/stderr as the channel. If the implementation prefers a different channel it must be
  reported, because this test will not accept it.
